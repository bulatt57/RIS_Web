## 2. Описание разработанной схемы (`db/schema.sql`)

Схема полностью соответствует ER-модели из `docs/data-model.md` и третьей нормальной форме (3НФ):

1. **`departments` (справочник подразделений ЕЦУиМС):**
   - `id` (`integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`)
   - `code` (`text NOT NULL UNIQUE`) — краткий код подразделения (`ACCESS`, `TRANSPORT`, `MONITORING`, `OPERATIONS`)
   - `name` (`text NOT NULL UNIQUE`) — название подразделения («Сеть доступа», «Транспортная сеть», «Мониторинг», «Эксплуатация»)
2. **`users` (пользователи системы):**
   - `id` (`integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`)
   - `full_name` (`text NOT NULL`)
   - `email` (`text NOT NULL UNIQUE`)
   - `role` (`text NOT NULL CHECK (role IN ('Manager', 'Engineer', 'Dispatcher'))`)
3. **`assignments` (главный объект — поручения):**
   - `id` (`integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`)
   - `number` (`text NOT NULL UNIQUE`) — регистрационный номер (`ПОР-2026-0001`)
   - `title` (`text NOT NULL CHECK (char_length(btrim(title)) BETWEEN 5 AND 80)`)
   - `description` (`text NOT NULL CHECK (char_length(btrim(description)) BETWEEN 10 AND 500)`)
   - `department_id` (`integer NOT NULL REFERENCES departments(id)`) — внешний ключ на справочник подразделений
   - `status` (`text NOT NULL DEFAULT 'New' CHECK (status IN ('New', 'InProgress', 'Closed', 'Cancelled'))`)
   - `created_at` (`timestamptz NOT NULL DEFAULT now()`)
   - `created_by_user_id` (`integer NOT NULL REFERENCES users(id)`) — создатель поручения
   - `assignee_user_id` (`integer NULL REFERENCES users(id)`) — назначенный исполнитель (допускает `NULL` для новых поручений)

### Индексы (п. 3.4 методички)
- `CREATE INDEX assignments_status_idx ON assignments (status);` — ускоряет выборку поручений по статусу (`WHERE status = 'New'`) и подсчёт статистики (`GROUP BY status`).
- `CREATE INDEX assignments_department_id_idx ON assignments (department_id);` — ускоряет соединение (`JOIN`) главной таблицы `assignments` со справочником подразделений `departments` и фильтрацию по подразделению.

### Безопасное повторное выполнение схемы (п. 5.3 методички)
В начале `db/schema.sql` указаны команды `DROP TABLE IF EXISTS assignments, users, departments CASCADE;`, благодаря чему схему можно многократно перезапускать на учебной базе `course_assignments` без ошибок существования объектов.

### 3.2. Запрос 2 — `JOIN` главной таблицы со справочником подразделений и пользователями

```sql
SELECT
    a.number,
    a.title,
    d.name AS department_name,
    u_creator.full_name AS created_by,
    COALESCE(u_assignee.full_name, 'Не назначен') AS assignee_name,
    a.status,
    a.created_at
FROM assignments AS a
JOIN departments AS d ON d.id = a.department_id
JOIN users AS u_creator ON u_creator.id = a.created_by_user_id
LEFT JOIN users AS u_assignee ON u_assignee.id = a.assignee_user_id
ORDER BY a.created_at DESC;
```

### 3.3. Запрос 3 — `GROUP BY` со счётчиком по всем четырём статусам

```sql
SELECT status, COUNT(*) AS count
FROM assignments
GROUP BY status
ORDER BY status;
```

**Результат выполнения (видны все 4 статуса):**

```text

------------+-------

 Closed     |     1

 New        |     2
(4 rows)
```

### 3.4. Запрос 4 — Проверка ограничения `CHECK` при вставке недопустимого статуса `'Done'` (п. 6.4)

Команда проверки:

```sql
INSERT INTO assignments (number, title, description, department_id, status, created_by_user_id)
VALUES ('ПОР-2026-9999', 'Проверка недопустимого статуса Done', 'Эта строка должна быть отклонена ограничением CHECK в PostgreSQL', 1, 'Done', 1);
```

**Отказ СУБД PostgreSQL:**

```text
ERROR:  new row for relation "assignments" violates check constraint "assignments_status_check"
DETAIL:  Failing row contains (6, ПОР-2026-9999, Проверка недопустимого статуса Done, Эта строка должна быть отклонена..., 1, Done, 2026-11-06 ..., 1, null).
```

Ошибочная вставка не включена в рабочий `db/seed.sql` (оставлена закомментированной в конце `db/queries.sql`).
