## 1. Цель работы

Реализовать на сервере `ASP.NET Core` (`http://localhost:5000`) маршруты главного объекта предметной области (`Assignments` / Поручения) с хранением в оперативной памяти: создание записи (`POST /api/assignments` → `201`), чтение списка (`GET /api/assignments` → `200`, включая `[]`), чтение одной записи (`GET /api/assignments/{id}` → `200` / `404`), отдельное назначение исполнителя (`PATCH /api/assignments/{id}/assignee` → `200`) и отдельную смену статуса (`PATCH /api/assignments/{id}/status` → `200` / `409`), а также настроить безопасное логирование сбоев без выдачи `stack trace` клиенту и подготовить коллекцию Postman.

## 2. Таблица реализованных маршрутов и кодов ответов

| Метод и путь | Код успеха | Коды отказа | Назначение и бизнес-правила |
|--------------|------------|-------------|-----------------------------|
| `POST /api/assignments` | `201 Created` | `400`, `500` | Создаёт поручение. Принимает только `title` (5–80 симв.), `departmentId` / `siteId` (> 0), `description` (10–500 симв.). Сервер сам задаёт `id`, `number` (`ПОР-2026-0003`), `status: "New"` и `assigneeUserId: null`. |
| `GET /api/assignments` | `200 OK` | `500` | Возвращает список всех поручений в памяти (если список пуст — возвращает `200 OK` и `[]`). |
| `GET /api/assignments/{id}` | `200 OK` | `404` | Возвращает одно поручение по `id` или `404 Not Found`, если записи нет. |
| `PATCH /api/assignments/{id}/assignee` | `200 OK` | `400`, `404` | Отдельно назначает исполнителя (`{ "assigneeUserId": 5 }`, целое число > 0). |
| `PATCH /api/assignments/{id}/status` | `200 OK` | `400`, `404`, `409` | Отдельно меняет статус (`New`, `InProgress`, `Closed`, `Cancelled`). Если исполнитель ещё не назначен (`assigneeUserId == null`), переход в `InProgress` отклоняется с кодом **`409 Conflict`**. |

## 3. Проверка обязательных запросов из коллекции (п. 5.2)

Коллекция сохранена в `docs/api-collection/assignments.postman_collection.json` (и продублирована как `docs/api-collection/tickets.postman_collection.json`):

1. **Успешный `POST /api/assignments`:**
   - Запрос: `{"title": "Проверить резервный канал связи на узле Б", "departmentId": 2, "description": "После грозы наблюдается затухание сигнала на резервной линии"}`
   - Ответ: **`201 Created`**, тело содержит серверные поля `"id": 3`, `"number": "ПОР-2026-0003"`, `"status": "New"`, `"assigneeUserId": null`.
2. **`POST /api/assignments` с коротким `title` из 3 символов (`"Абв"`):**
   - Ответ: **`400 Bad Request`** (`ValidationProblemDetails`: поле `title` должно содержать от 5 до 80 символов).
3. **`GET /api/assignments/999999`:**
   - Ответ: **`404 Not Found`** (`ProblemDetails`: поручение с `id=999999` не существует).
4. **`PATCH /api/assignments/1/status` (`{"status": "InProgress"}`) без назначенного исполнителя:**
   - Ответ: **`409 Conflict`** (`Нельзя перевести поручение в статус InProgress, пока не назначен исполнитель`).
5. **Оба `PATCH` после назначения исполнителя:**
   - Сначала `PATCH /api/assignments/1/assignee` с `{"assigneeUserId": 5}` → **`200 OK`** (`"assigneeUserId": 5`).
   - Затем `PATCH /api/assignments/1/status` с `{"status": "InProgress"}` → **`200 OK`** (`"status": "InProgress"`).

## 4. Лог неожиданной ошибки и безопасный ответ 500 (п. 5.3)

При временном вызове учебного исключения `throw new InvalidOperationException("Simulated unexpected failure after validation")` после валидации в `AssignmentsController.Create`:

1. **Строка в логе сервера (терминал `dotnet run`):**
   ```text
   fail: backend.Controllers.AssignmentsController[0]
         CreateAssignment failed; departmentId=2; error=InvalidOperationException
   ```
   *(Место для скриншота строки лога в терминале: `![Скриншот лога ошибки в терминале](lab-08-error-log.png)`).*

2. **Безопасный ответ клиенту (`500 Internal Server Error`, `application/problem+json`):**
   ```json
   {
     "type": "https://tools.ietf.org/html/rfc9110#section-15.6.1",
     "title": "Сервер не смог обработать запрос",
     "status": 500,
     "detail": "Неожиданный сбой при создании записи."
   }
   ```
   В ответе клиенту отсутствуют `stack trace`, абсолютные пути файловой системы, тело запроса целиком и секреты. Перед коммитом учебный сбой закомментирован.

## 6. Ответы на вопросы для устной защиты (§7 методички)

### 1. Почему назначение исполнителя и смена статуса — два отдельных `PATCH`, а не один общий?
Назначение ответственного сотрудника (`/assignee`) и изменение этапа жизненного цикла поручения (`/status`) — это две разные бизнес-операции с разными входными данными и правилами проверки. Например, руководитель подразделения назначает исполнителя, а сам исполнитель позже переводит задачу в работу (`InProgress`) или закрывает её (`Closed`). Разделение на два узких `PATCH`-маршрута делает API предсказуемым и не позволяет случайно перезаписать чужие поля.

### 2. Чем код `400` отличается от `409`?
- **`400 Bad Request`** означает, что сам входной запрос некорректен по форме или значениям полей (невалидный JSON, тема короче 5 символов, `departmentId <= 0`, неизвестное название статуса). Такой запрос нельзя выполнить ни при каком состоянии записи.
- **`409 Conflict`** означает, что синтаксис JSON и сами значения полей корректны (`"status": "InProgress"` — допустимый статус), но операция противоречит текущему состоянию объекта в бизнес-процессе (у поручения ещё не назначен исполнитель `assigneeUserId == null`).

### 3. Почему пустой список возвращает `200`, а не `404`?
Маршрут `GET /api/assignments` обращается к ресурсу-коллекции. Сам маршрут и коллекция существуют, просто в данный момент в ней `0` элементов, поэтому возвращается успешный статус `200 OK` и пустой массив `[]`. Статус `404 Not Found` возвращается только тогда, когда клиент запрашивает конкретную запись по идентификатору (`GET /api/assignments/999999`), которой нет.

### 4. Что видит клиент и что видит разработчик при неожиданном сбое (`500`)?
- **Клиент** получает стандартный безопасный объект `ProblemDetails` с кодом `500` и общим сообщением («Сервер не смог обработать запрос») без `stack trace`, внутренних путей сервера и деталей исключения.
- **Разработчик** видит в серверном логе структурированную запись об ошибке (`CreateAssignment failed; departmentId=2; error=InvalidOperationException`), по которой можно сразу понять, какая операция, на каких параметрах и с каким типом исключения завершилась сбоем.
