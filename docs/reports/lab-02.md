## 4. Ответы на вопросы для устной защиты

### 1. Почему название подразделения (участка) не хранится текстом в каждом поручении?
Согласно требованиям третьей нормальной формы (3НФ), неключевые атрибуты должны зависеть только от первичного ключа своей таблицы. Название подразделения ЕЦУиМС (например, «Сеть доступа» или «Мониторинг») хранится один раз в справочнике `Department`, а в таблице поручений `Assignment` хранится только числовой внешний ключ `departmentId`. Если бы название дублировалось текстом в каждой строке `Assignment`, то при переименовании отдела пришлось бы обновлять сотни записей, что могло бы привести к рассинхронизации данных (аномалии обновления).

### 2. Чем машинный `id` отличается от человеческого номера `number` (`ПОР-2026-0001`)?
- `id` — это внутренний технический первичный ключ (`PK`) записи в базе данных. Он используется для быстрых связей между таблицами (`FK`) и подставляется в URL-адреса запросов API (например, `/api/assignments/17`).
- `number` (`ПОР-2026-0001`) — это бизнес-атрибут для людей (руководителя и исполнителей ЕЦУиМС), по которому удобно называть поручение на планёрке или искать его глазами в таблице. Формат человеческого номера может поменяться по регламенту компании, но технический `id` и все связи в БД останутся неизменными.

### 3. Почему назначение исполнителя и смена статуса — это два разных `PATCH`-запроса?
Это разные бизнес-операции с разными правами доступа по ролям (согласно ЛР1):
- Назначать исполнителя (`PATCH /api/assignments/{id}/assignee`) имеет право **только руководитель (`Manager`)** (ФТ-4, ФТ-9).
- Переводить поручение в работу (`PATCH /api/assignments/{id}/status`) должен **назначенный исполнитель (`Executor`)** (ФТ-5, ФТ-10).
Разделение на два эндпоинта позволяет серверу чётко проверять права ролей и гарантирует, что при смене статуса случайно не затрётся исполнитель (и наоборот).

### 4. Почему браузер не пишет в PostgreSQL напрямую?
Браузерный код (`Vue 3`) выполняется на устройстве пользователя и не является доверенной средой. Если дать браузеру прямой доступ к `PostgreSQL`, любой сотрудник сможет обойти проверки ролей (`Manager` / `Executor` / `Viewer`), изменить чужое поручение, подделать дату создания или удалить таблицы. Сервер `ASP.NET Core` выступает единственным защищённым посредником, который проверяет JWT-токен, валидирует входные данные и обеспечивает единый источник правды.
